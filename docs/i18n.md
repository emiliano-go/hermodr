# Locales

The i18n foundation lives in `src/lib/i18n/`. English is the source catalog in
`locales/en.json`; Arabic is in `locales/ar.json`. Catalogs cover component,
Settings and application-state copy alongside native reason codes. Whole-source
integration and native error migration continue under issue #216. Required RTL
visual verification remains pending; source and SSR checks do not prove layout.

Import `t`, `formatMessage`, `formatDate`, `formatTime`, `formatNumber` and
`formatRelative` from `localizer.ts`. This module works in Node without Svelte or
browser globals. `MessageKey` is derived from English; native error codes can
use the string signature. `hasMessage` identifies known source keys. Unknown
codes return readable text; error callers should select `error.operation_failed`
when a native code is unknown. Missing translations use English, never the key.

Messages are strings with named scalar parameters, such as `{language}`, or
plural objects with `other` and optional `zero`, `one`, `two`, `few`, `many`.
Plural messages require numeric `count`; `Intl.PluralRules` selects the form.
Arabic uses all six categories. A form can omit `count` when grammar expresses
the number, such as the dual form. Missing named parameters fall back to English
or `locale.text_unavailable`. Pass identifiers as strings; number parameters use
the selected locale. Catalog text is never interpreted as HTML. Render it as
normal escaped Svelte text, never through `{@html}`.

Date and time helpers accept Unix **seconds**. Relative formatting accepts a
value and an `Intl.RelativeTimeFormat` unit. Wire values, message sorting, IDs
and native input values remain unchanged. Display formatting follows the active
locale. In System mode, an unsupported system language uses English text while
date/number formatting retains the valid system locale.

`locale.svelte.ts` owns preference, resolved formatting locale, catalog language,
direction, loading and structured error state. `locale.errorText` is reactive.
The client init hook initializes it before the SPA starts. Device preference
`postal.locale` is `system`, `en` or `ar`; it is independent of accounts. Storage
events synchronize windows, including floats. System mode follows language
changes. Arabic loads lazily; English is available immediately. Failed reads,
saves or catalog loads remain visible in `locale.error`. A failed save applies
the choice for this session; it does not claim persistence. A failed catalog
load uses English and LTR. `dispose()` removes listeners and cancels late loads.

To add a locale:

1. Add one JSON catalog beside English, keeping source keys and parameter names.
2. Add its language, native name and direction to the localizer's registry and
   preference types, then add its explicit lazy loader.
3. Update the reactive preference validation and Settings choices.
4. Check key coverage, named parameters, plurals, fallback, formatting, device
   persistence, live changes and document attributes.
5. Review logical layout and bidi behavior for RTL. Actual visual verification
   needs an authorized browser or native-window pass; source tests do not prove it.

Store codes and parameters for notices and errors, then format during rendering.
Formatting once into a cached string prevents existing UI from changing language.
Do not translate protocol discriminants, user messages, contact names or IDs.

## Scheduled failures on disk

New `scheduled_messages.error` values remain SQL `TEXT`, containing a JSON
envelope with `format: "postal_scheduled_failure_v1"` and a `failure` object.
The object contains `code`, scalar `params`, and optional technical `diagnostic`.
New values contain no translated product text. Interrupted sends receive
`error.scheduled_interrupted` during normal startup recovery.

Reading recognizes only version one. Legacy strings, malformed envelopes, and
unknown future formats use localized fallback descriptors and retain the full
original value as diagnostic detail. Reading does not rewrite existing rows.
New failure writes use the envelope; startup recovery still changes only rows
whose status was `sending` to `uncertain`. Status, attempted flag, ordering,
message IDs, and manual retry behavior retain their existing meanings.

The native scheduled-message view keeps the raw `error` field for compatibility
and exposes decoded `failure` for rendering. Render that descriptor, never the
raw stored value. An earlier client without this decoder cannot interpret the
envelope as localized failure text. Future format changes need another explicit
version and a compatibility reader.
